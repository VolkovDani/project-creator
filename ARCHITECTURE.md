# Архитектурные контракты

Статус: API и направления развития согласованы; основное хранилище выбрано
в [ADR-001](docs/adr/001-postgresql-pgvector.md). SSE реализован через PostgreSQL-журнал событий и клиентский адаптер кеша.
RAG и анализ возможных коллизий реализованы с локальными адаптерами Ollama.
Экспериментальный генератор OpenVINO на Intel NPU выбирается отдельно;
его проверенные возможности и ограничения описаны в [ADR-002](docs/adr/002-openvino-npu.md).
Полный локальный запуск и эксплуатация описаны в корневом README.

## API и актуальность схемы

Бэкенд на Go предоставляет GraphQL для чтения и изменения данных.
Фронтенд — Next.js + TypeScript. SSE используется отдельным каналом событий.

Источник API-контракта — SDL в репозитории. Из одной схемы генерируются
серверные привязки и типы/типизированные документы операций клиента.
Фронтенд получает актуальный контракт при разработке и сборке через codegen;
он не скачивает схему на каждый запрос и не изменяет свой код автоматически
при обновлении бэкенда.

CI проверяет корректность SDL, совместимость операций фронтенда со схемой
и отсутствие изменений после Go/TypeScript codegen. Отдельное сравнение
несовместимых изменений с предыдущей версией API и включение версии/хеша
контракта в сборки пока не реализованы и остаются требованиями дальнейшего развития.
Независимый выпуск фронтенда и бэкенда требует
переходного периода совместимости и постепенного удаления полей.
Версия контракта не является ключом инвалидации данных.

## Общая валидация

Рядом с SDL храним машиночитаемый контракт ограничений полей, связанный с
GraphQL input types. Типы и допустимость null определяются SDL; требования
непустого значения, длины и другие ограничения содержимого задаются общим
контрактом. Например, `description: String!` требует строку, но допускает
пустое значение, поскольку в JSON-контракте у описания `required: false`.
В MVP используются JSON-контракты версии 1: `contracts/project.json` и
`contracts/requirement.json`, которые напрямую читают адаптеры Go и TypeScript.

Из этого контракта получаем проверки Go и TypeScript либо адаптеры к выбранным
валидаторам. Нельзя считать, что одних GraphQL типов достаточно для правил формы.
Отдельного генератора ограничений пока нет: неподдерживаемые версии и правила
отклоняются адаптерами и проверяются общими тестами. В Go контракт загружается
при инициализации пакета; неподдерживаемое правило нельзя молча пропустить.

Семантика ограничений фиксируется явно: trim и нормализация, пустая строка/null,
единица длины Unicode, формат чисел и дат. Регулярные выражения применяем только
в совместимом подмножестве или заменяем именованными валидаторами.
Один набор примеров проверяется тестами Go и TypeScript.

Фронтенд проверяет доступные ему ограничения для быстрого ответа пользователю.
Бэкенд повторяет общую валидацию и проверяет права и состояние данных.
Проверки уникальности, зависимостей и новых бизнес-правил при их введении также
должны выполняться на сервере. Предварительная удалённая проверка
не отменяет проверку в момент мутации и ограничения хранилища.

## Ошибки ввода

Ожидаемые ошибки валидации возвращаются в типизированном payload мутации.
Текущие валидаторы собирают ошибки всех полей за один вызов, возвращая одну
ошибку на нарушенное поле. Несколько ошибок одного поля — требование для
дальнейшего расширения валидаторов и их отображения.

Пример текущего payload создания проекта из `graph/schema.graphqls`:

```json
{
  "project": null,
  "fieldErrors": [
    {
      "path": ["input", "name"],
      "code": "MAX_LENGTH",
      "messageKey": "validation.maxLength",
      "params": [{"key": "max", "value": 120}]
    }
  ]
}
```

Путь — массив строковых сегментов. Адаптер формы удаляет корневой сегмент input
и сопоставляет оставшийся путь полю. В SDL параметры — список `ErrorParam`
с `key: String!` и `value: Int!`; фронтенд преобразует его в словарь для перевода.
Вложенные input-сущности, пути с индексами массивов, отдельный `formErrors`
и другие типы параметров пока не представлены в SDL. Их добавление требует
расширения контракта с сохранением стабильных code/messageKey.

Синтаксические ошибки GraphQL, ошибки coercion входных типов, авторизации и
неожиданные сбои обрабатываются отдельно: транспортный адаптер приводит
доступные структурированные сведения к общему представлению UI.
Нельзя разбирать текст стандартной ошибки GraphQL, чтобы извлечь поле;
при отсутствии надёжного пути показывается общая ошибка.
Внутренние сообщения и stack trace пользователю не передаются.

## SSE и кеш

Бэкенд выдаёт стабильные теги зависимостей данных, а не внутренние ключи
выбранной frontend-библиотеки. В MVP это `projects`, `project:<id>` и
`project:<id>:requirements`. Ответы GraphQL передают их в `extensions.cacheTags`;
область workspace проверяется до выдачи данных и событий.
Клиентский адаптер связывает теги с кешированными операциями и переменными.

После успешной транзакции сервер публикует cache.invalidate:

```json
{
  "schemaVersion": 1,
  "keys": ["projects", "project:123", "project:123:requirements"]
}
```

Каждое SSE-событие имеет непрозрачный id для курсора восстановления.
При появлении, удалении или переносе сущности инвалидируются также зависимые
списки, счётчики и результаты поиска. Область события ограничена правами получателя;
идентификаторы ресурсов тоже считаются данными, требующими защиты.

Клиент помечает затронутые записи устаревшими и перечитывает активные запросы.
Повторные события безопасны; серии событий можно объединять.
Событие, пришедшее во время запроса, не должно позволять позднему старому ответу
пометить данные свежими: клиент учитывает поколение инвалидации и повторяет запрос.

Реализованы heartbeat, reconnect с backoff и восстановление по Last-Event-ID.
Если курсор устарел или события потеряны, сервер сообщает cache.reset:
клиент сбрасывает соответствующий кеш и перечитывает активные данные.
При первом подключении или новом подключении без курсора также выполняется
сверка/повторное чтение. Для обычного restart страницы, offline/online и смены
пользователя предусматривается явное восстановление актуальности.

Авторизация SSE согласуется с авторизацией GraphQL. В локальном MVP Next.js
проксирует same-origin запросы и хранит workspace-токен только на сервере;
токены не передаются в URL. Защищённые cookie-сессии и полноценная пользовательская
аутентификация — будущие возможности, не реализованные этим локальным режимом.
Отзыв доступа требует очистки данных, а не только фонового refetch.
При нескольких экземплярах бэкенда необходим общий канал событий.
Публикация после commit должна учитывать сбой между записью и отправкой:
используем transactional outbox либо эквивалентную гарантию с восстановлением.

SSE обновляет кеш данных в браузере. Если подключаем серверный кеш Next.js,
его инвалидация проектируется отдельно; браузерное событие само его не обновляет.
До этого авторизованные изменяемые данные не должны зависеть от долгоживущего
серверного кеша Next.js.

## i18n

Общие словари храним в репозитории в формате, который читают Go и TypeScript.
Все интерфейсные тексты, подписи, уведомления и пользовательские ошибки используют
ключи. Пользовательский контент, имена собственные и технические логи не переводятся.

Ошибки API в первую очередь передают messageKey и params, фронтенд переводит их
в текущей локали. Смена языка не меняет code ошибки. Серверные письма и общий
Go-renderer переводов пока не реализованы; при их появлении следует использовать
те же словари, а не независимые переводы.

При выборе библиотек проверяем совместимость интерполяции, множественных чисел,
экранирования и форматирования дат/чисел. До этого используем только общее
поддерживаемое подмножество. Сейчас Go-тесты проверяют наличие ключей ошибок
валидации RU/EN и параметра `{max}`, а Go/TypeScript используют общие примеры
валидации. Полная проверка паритета словарей/параметров, общих примеров рендеринга
переводов Go/TypeScript и линтер захардкоженных UI-строк ещё не реализованы;
это остаётся требованием расширения CI.
Для неизвестного ключа предусмотрено локализованное общее сообщение.

## Технический срез и дальнейшие проверки по TDD

В MVP реализованы создание/чтение карточек проектов и создание, редактирование
и удаление требований. Редактирования паспорта проекта в текущей SDL нет.
Для дальнейшего расширения сохраняем сквозной сценарий:
GraphQL query/mutation → серверная валидация → сохранение → SSE invalidation →
обновление списка и карточки в Next.js, с переводами и ошибками полей.

Сначала пишем падающие тесты поведения. Проверяем:
валидный ввод; общие ограничения на обеих сторонах; серверную ошибку поля;
вложенные пути; изоляцию клиентов; отсутствие события при rollback;
обновление двух открытых клиентов; повтор события; reconnect/reset;
событие во время запроса; одинаковые переводы и параметры.

Реализованные сценарии проверяются unit/integration/GraphQL/Playwright-тестами.
Вложенные сущности и остальные расширения из списка добавляются отдельными
задачами; перечисление проверок не означает, что эти возможности уже реализованы.


## Хранилище и поиск

PostgreSQL хранит проекты и требования. Расширение pgvector подготавливается
миграциями и проверяется при старте. Индексация хранит точные фрагменты и версии источников, профиль модели и
векторы размерности 1024. Используется точный cosine-поиск; HNSW и hybrid retrieval пока нет.
PostgreSQL Full-Text Search и объединение выдач остаются направлениями развития.
Область workspace/project применяется до поиска и передачи источников модели.
Переход с SQLite не меняет SDL, правила валидации или optimistic locking.
Инструкции запуска, миграций и переноса локальных данных находятся в README.


### Решение для доставки событий в MVP

`cache_events` — транзакционный журнал с триггерами PostgreSQL и polling;
удержание advisory lock до commit обеспечивает порядок видимости номеров.
SSE читает журнал в repeatable-read snapshot, фильтруя workspace до выдачи.
История последних 1000 событий ограничена; потеря курсора требует reset/refetch.
Реализация использует общие теги проектов в пределах workspace, без информации
из закрытых результатов. Метаданные GraphQL находятся в extensions.cacheTags.
Подробности эксплуатации и текущие ограничения описаны в корневом README.


## Анализ требований локальной моделью

Миграция004 хранит попытки анализа и снимки ID/версий/текстов источников.
Явная мутация запуска использует текущий RAG только внутри авторизованного проекта;
генератор сравнивает ограниченный набор пар с готовыми актуальными embeddings.
Источники являются недоверенными данными, ответ проходит проверку схемы и ссылок.
Возможная коллизия — предложение для человека; отсутствие найденных коллизий не
означает полноту retrieval. Конкурентные попытки, timeout, retry и профили моделей
изолированы; изменившиеся источники делают результат устаревшим. Ограничения и
настройка Ollama описаны в корневом README; экспериментальный NPU-генератор —
в [инструкции NPU](docs/intel-npu.md).


## Локальное развёртывание MVP

Docker Compose запускает Next.js, Go API, PostgreSQL с pgvector и Ollama.
На хост публикуется только интерфейс на loopback; backend, PostgreSQL и Ollama
доступны по сети Compose. Next.js хранит workspace-токен только на сервере.
Это локальный однопользовательский режим, а не публичная система авторизации.

Миграции выполняются backend до приёма запросов. Healthchecks отделяют готовность
процессов/БД от наличия и качества моделей. Веса загружаются явно, их полные
digests закрепляются настройкой. Изменение embedding-профиля требует
переиндексации и нового анализа; смена только генератора требует нового анализа,
сохраняя пригодность существующих векторов.
Автоматической загрузки моделей или скрытого облачного fallback нет.
PostgreSQL и веса Ollama хранятся в отдельных постоянных volumes.
Для экспериментального NPU-профиля OpenVINO runtime, экспортированные веса,
манифест и кеш находятся на хосте в локальном каталоге `.npu/`; Docker Compose
подключает backend к уже запущенному host runtime через Unix socket.

Обычный container-smoke использует отдельный Compose-проект и детерминированную
заглушку Ollama только из тестового override. Он проверяет весь HTTP-путь,
миграции и сохранность после перезапуска; качество настоящей LLM проверяется
отдельным явным запуском. Команды запуска, проверки, backup/restore и удаления
данных находятся в корневом README.
