# Архитектурные контракты

Статус: API и направления развития согласованы; основное хранилище выбрано
в [ADR-001](docs/adr/001-postgresql-pgvector.md). Контракты SSE и RAG ниже описывают
будущее поведение и не означают, что эти компоненты уже реализованы.

## API и актуальность схемы

Бэкенд на Go предоставляет GraphQL для чтения и изменения данных.
Фронтенд — Next.js + TypeScript. SSE используется отдельным каналом событий.

Источник API-контракта — SDL в репозитории. Из одной схемы генерируются
серверные привязки и типы/типизированные документы операций клиента.
Фронтенд получает актуальный контракт при разработке и сборке через codegen;
он не скачивает схему на каждый запрос и не изменяет свой код автоматически
при обновлении бэкенда.

CI должен проверять корректность SDL, совместимость операций фронтенда со схемой,
результат генерации и несовместимые изменения. Сборки получают версию/хеш
контракта для диагностики. Независимый выпуск фронтенда и бэкенда требует
переходного периода совместимости и постепенного удаления полей.
Версия контракта не является ключом инвалидации данных.

## Общая валидация

Рядом с SDL храним машиночитаемый контракт ограничений полей, связанный с
GraphQL input types. Базовые типы и обязательность берутся из SDL; дополнительные
ограничения (длины, диапазоны, форматы) описываются один раз.
Формат контракта и генераторы выбираются при реализации.

Из этого контракта получаем проверки Go и TypeScript либо адаптеры к выбранным
валидаторам. Нельзя считать, что одних GraphQL типов достаточно для правил формы.
Неподдерживаемое генератором правило должно обнаруживаться при сборке:
его нельзя молча пропустить.

Семантика ограничений фиксируется явно: trim и нормализация, пустая строка/null,
единица длины Unicode, формат чисел и дат. Регулярные выражения применяем только
в совместимом подмножестве или заменяем именованными валидаторами.
Один набор примеров проверяется тестами Go и TypeScript.

Фронтенд проверяет доступные ему ограничения для быстрого ответа пользователю.
Бэкенд повторяет все проверки и выполняет проверки уникальности, прав,
состояния данных, зависимостей и бизнес-правил. Предварительная удалённая проверка
не отменяет проверку в момент мутации и ограничения хранилища.

## Ошибки ввода

Ожидаемые ошибки валидации возвращаются в типизированном payload мутации.
Для одной отправки допустимы несколько ошибок, в том числе несколько на поле.

Пример формы ошибки (схематичный JSON, окончательный SDL появится с реализацией):

```json
{
  "fieldErrors": [
    {
      "path": ["input", "blocks", "0", "name"],
      "code": "ALREADY_EXISTS",
      "messageKey": "validation.alreadyExists",
      "params": {}
    }
  ],
  "formErrors": []
}
```

Путь — массив сегментов, индексы массивов передаются десятичными строками.
Адаптер формы удаляет корневой сегмент input и сопоставляет оставшийся путь полю.
Общие ошибки идут в formErrors с теми же code/messageKey/params, без path.
Параметры имеют явно заданные скалярные типы в окончательной схеме.

Синтаксические ошибки GraphQL, ошибки coercion входных типов, авторизации и
неожиданные сбои обрабатываются отдельно: транспортный адаптер приводит
доступные структурированные сведения к общему представлению UI.
Нельзя разбирать текст стандартной ошибки GraphQL, чтобы извлечь поле;
при отсутствии надёжного пути показывается общая ошибка.
Внутренние сообщения и stack trace пользователю не передаются.

## SSE и кеш

Бэкенд выдаёт стабильные теги зависимостей данных, а не внутренние ключи
выбранной frontend-библиотеки. Например: product:123, product:123:blocks.
Ответы чтения связываются с тегами через единый контракт метаданных,
конкретное представление которого выбирается при реализации.
Клиентский адаптер связывает теги с кешированными операциями и переменными.

После успешной транзакции сервер публикует cache.invalidate:

```json
{
  "schemaVersion": 1,
  "keys": ["product:123", "product:123:blocks"]
}
```

Каждое SSE-событие имеет непрозрачный id для курсора восстановления.
При появлении, удалении или переносе сущности инвалидируются также зависимые
списки, счётчики и результаты поиска. Область события ограничена правами получателя;
идентификаторы ресурсов тоже считаются данными, требующими защиты.

Клиент помечает затронутые записи устаревшими и перечитывает активные запросы.
Повторные события безопасны; серии событий можно объединять.
Событие, пришедшее во время запроса, не должно позволять позднему старому ответу
пометить данные свежими: клиент учитывает поколение инвалидации и повторяет запрос.

Нужны heartbeat, reconnect с backoff и восстановление по Last-Event-ID.
Если курсор устарел или события потеряны, сервер сообщает cache.reset:
клиент сбрасывает соответствующий кеш и перечитывает активные данные.
При первом подключении или новом подключении без курсора также выполняется
сверка/повторное чтение. Для обычного restart страницы, offline/online и смены
пользователя предусматривается явное восстановление актуальности.

Авторизация SSE согласуется с авторизацией GraphQL. Предпочтителен same-origin
маршрут с защищённой сессионной cookie; токены не передаются в URL.
Отзыв доступа требует очистки данных, а не только фонового refetch.
При нескольких экземплярах бэкенда необходим общий канал событий.
Публикация после commit должна учитывать сбой между записью и отправкой:
используем transactional outbox либо эквивалентную гарантию с восстановлением.

SSE обновляет кеш данных в браузере. Если подключаем серверный кеш Next.js,
его инвалидация проектируется отдельно; браузерное событие само его не обновляет.
До этого авторизованные изменяемые данные не должны зависеть от долгоживущего
серверного кеша Next.js.

## i18n

Общие словари храним в репозитории в формате, который читают Go и TypeScript.
Все интерфейсные тексты, подписи, уведомления и пользовательские ошибки используют
ключи. Пользовательский контент, имена собственные и технические логи не переводятся.

Ошибки API в первую очередь передают messageKey и params, фронтенд переводит их
в текущей локали. Для серверных писем и других самостоятельных сообщений Go
использует те же словари. Смена языка не меняет code ошибки.

При выборе библиотек проверяем совместимость интерполяции, множественных чисел,
экранирования и форматирования дат/чисел. До этого используем только общее
поддерживаемое подмножество. CI проверяет наличие ключей, согласованность параметров,
отсутствие захардкоженных UI-строк и общие примеры рендеринга Go/TypeScript.
Для неизвестного ключа предусмотрено локализованное общее сообщение.

## Первый технический срез по TDD

Создание и редактирование паспорта продукта:
GraphQL query/mutation → серверная валидация → сохранение → SSE invalidation →
обновление списка и карточки в Next.js, с переводами и ошибками полей.

Сначала пишем падающие тесты поведения. Проверяем:
валидный ввод; общие ограничения на обеих сторонах; серверную ошибку поля;
вложенные пути; изоляцию клиентов; отсутствие события при rollback;
обновление двух открытых клиентов; повтор события; reconnect/reset;
событие во время запроса; одинаковые переводы и параметры.

Начальная реализация оформляется отдельной задачей: этот документ не означает,
что перечисленные механизмы уже реализованы.


## Хранилище и поиск

PostgreSQL хранит проекты и требования. Расширение pgvector подготавливается
миграциями и проверяется при старте. Размерность векторов и схема embeddings
появятся вместе с ingestion и поиском в #7; HNSW и hybrid retrieval пока нет.
PostgreSQL Full-Text Search и объединение выдач рассматриваются в том же этапе.
Область workspace/project применяется до поиска и передачи источников модели.
Переход с SQLite не меняет SDL, правила валидации или optimistic locking.
Инструкции запуска, миграций и переноса локальных данных находятся в README.
