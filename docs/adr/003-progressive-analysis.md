# ADR-003: асинхронный анализ с сохранением каждой пары

Статус: реализовано для задачи #32. Дата: 2026-10-30.

## Контекст

Последовательная проверка20 пар на локальном NPU может занимать больше общего
лимита180 секунд. Синхронная мутация удерживала HTTP-запрос и показывала результаты
только после завершения пакета. Ошибка скрывала прогресс, а новый запуск повторял
уже выполненные сравнения.

## Решение

Сохраняем очередь запусков и до20 кандидатных пар в PostgreSQL `analysis_runs`.
Стадия, список пар, снимки источников, результаты, текущая пара и счётчики
обновляются одной записью. JSONB подходит небольшому ограниченному списку и
позволяет читать согласованный прогресс без отдельных запросов к каждой паре.
Существующий outbox-триггер публикует инвалидацию после commit.

`startProjectAnalysis` возвращает ID и начальное состояние. Worker внутри
приложения выбирает сохранённые задания. Session advisory lock на выделенном
соединении сериализует работу разных экземпляров backend; SQL-транзакции не
удерживаются во время запросов модели. Сохраняем последовательную генерацию,
текущий retrieval и ограничения100 требований/20 пар, без нового брокера,
микросервиса или внешнего провайдера.
Экземпляры backend, использующие одну очередь, должны иметь согласованные
профили моделей. Ожидающий запуск с прежним профилем завершается как
`PROFILE_CHANGED`; новый анализ выбирается явно с актуальной конфигурацией.

Отдельные бюджеты:180 секунд подготовки,120 секунд на пару. Работа использует
возобновляемый lease30 секунд с heartbeat5 секунд и токен владельца. Запись
результата проверяет владельца и действующий lease. Потеря соединения блокировки
отменяет работу; существующая сериализация в локальном runtime остаётся
дополнительной защитой от ещё завершающегося native inference.

При первой ошибке останавливаем пакет: текущая пара становится `failed`,
остальные ожидающие — `failed/NOT_PROCESSED`. Это учитывает NPU runtime, которому
после timeout может требоваться явный перезапуск. `processedPairs` считает
готовые и фактически начатые ошибочные сравнения, исключая `NOT_PROCESSED`.
До сохранения полного списка кандидатов `totalPairs` остаётся `null`.

Явный `retryProjectAnalysis` переиспользует ID последней попытки и повторяет
только ошибочные пары. Завершённые пары сохраняют ID, порядок и источники.
Изменённый снимок, профиль или более новый запуск запрещают такой повтор;
новый полный анализ создаёт отдельную попытку.

## Последствия и ограничения

Обновление вкладки и reconnect SSE перечитывают сохранённый прогресс.
Очередь возобновляется после рестарта. Штатная остановка завершает активную
работу как прерванную; после аварии это делает recovery по истечении lease.
Прерванные вызовы автоматически не повторяются. Очередь не имеет lease,
пока worker не захватил её; ожидающие задания не истекают из-за занятой модели.

Изменённые источники и профили делают прежние результаты устаревшими.
Исторические находки мигрируются со снимками; старым ошибочным попыткам не
приписывается неизвестное общее число кандидатов. Вердикты модели остаются
предложениями для проверки человеком. Новая схема выполнения не повышает
точность локальной модели и не обещает полного поиска противоречий.

Детерминированные тесты проверяют очередь, отмену HTTP, промежуточные commit,
права, источники, повтор, restart/lease, сериализацию разных экземпляров и
обновление интерфейса. Проверки реальной модели остаются отдельными opt-in.
