# Оценка классификации

[English version](classification-evaluator.md)

Синтетические русскоязычные примеры охватывают две оси таксономии, короткие и составные записи и воздержание. Эталонные метки задают ожидаемый результат теста. Запустите проверки из корня проекта с Python 3.10 или новее и контрактом классификации из #49.

```sh
python3 -B scripts/classification-evaluator_test.py
python3 -B scripts/classification-evaluator.py --contract contracts/classification.json --examples testdata/classification/synthetic.json --self-check
```

Для независимых прогонов замените `--self-check` на `--predictions ФАЙЛ`. Передайте JSON-объект, в котором каждой схеме (например, `flat` или `hierarchical`) соответствует массив объектов с уникальным `id` примера и полями `semantic` и `representation`. Воздержание обозначается null. Каждая схема должна покрывать ровно те же ID, что и эталон. Для каждой оси вычисляются число примеров, precision, recall, F1, матрица ошибок, покрытие и общая доля верных ответов. Неопределённое отношение записывается как null. Воздержание учитывается в знаменателях полноты и общей доли верных ответов. Явная метка `unknown` участвует как класс.

Самопроверка копирует эталонные метки и имитирует полное воздержание без вызова модели. Для выбора рабочих порогов нужны независимо проверенные метки, прогоны модели и зафиксированные версии checkpoint и вопросов. Храните приватные примеры и предсказания локально вне Git.

## Эксперимент на отдельных записях

Дополнительные пакеты Python не требуются. Детерминированная интеграционная проверка на loopback запускается командой `python3 -B scripts/classification_benchmark_test.py`. Эксперимент выполняется отдельно от приложения и исторического классификатора пар.

Кандидаты из открытых источников находятся в `testdata/classification/public-ru-proposed.json`. До первого вызова модели человек проверяет исходные отрывки и обе оси. Сохраните проверенный набор отдельно, например в `logs/issue50/reviewed.json`. Сохраните ссылки на источники, атрибуцию, уведомления о лицензиях, тексты, ID и заранее назначенное разделение по источникам. Установите верхнеуровневое поле `status` в `reviewed`, сохраните `language: ru` и версию контракта в `taxonomy`, добавьте `reviewer` и `reviewed_at` (дата ISO). Замените объект `proposed` в каждой записи на проверенные поля `semantic` и `representation` непосредственно в записи. Исключите несогласованные эталоны или явно укажите `unknown` на неоднозначной оси, если это соответствует правилам. Сохраните обе выборки. Перенос источников между выборками после просмотра предсказаний лишает контрольную выборку независимости.

Для проверенного набора используйте доверенный loopback с установленной GGUF-моделью `laya:322m-multilingual-bf16` и Ollama 0.40.16. Скрипт проверяет digest исследованного манифеста, движок, размер головы и локальный тег. Перед каждым вызовом inference и сразу после него проверяется идентичность модели. Передаётся одна запись или один отрывок с одним вопросом. Параметры качества в примере иллюстрируют запуск. Выберите оба значения до просмотра предсказаний.

```sh
mkdir -p logs/issue50
python3 -B scripts/classification-evaluator.py --run-local \
  --examples logs/issue50/reviewed.json --contract contracts/classification.json \
  --port 11434 --digest c1242e4a83f0e1cb58f0f191a65bbc5d3306fae274d152b8229ec574999d465d \
  --full-state-bytes 65536 --marker-state-bytes 384 \
  --target-precision 0.90 --min-accepted 5 > logs/issue50/run.json
```

Если Ollama доступна только внутри Compose, запустите интерпретатор Python в сетевом пространстве имён контейнера Ollama для доступа к его loopback. Смонтируйте репозиторий только для чтения, направьте stdout в отчёт на хосте. Рядом с отчётом укажите оборудование и конфигурацию runtime. В отчёт входят время начала в UTC, идентификаторы модели и кода, хеши точных файлов примеров и таксономии, отправленные вопросы, соответствия вариантов и исходные оценки каждого выполненного шага.

| Профиль | Вопрос и вход |
| --- | --- |
| `flat` | По полному тексту выбрать из всех меток каждой оси отдельно. |
| `flat_reverse`, `flat_reword` | Изменить в плоском профиле только порядок вариантов или только русские формулировки критериев. |
| `hierarchical` | Для каждой оси выбрать широкую группу, затем метку внутри группы. Группа с одной меткой даёт её сразу. |
| `story_probe` | Отдельно спросить, является ли полный текст пользовательской историей. Для сравнения привести проверенную форму записи к двум классам. |
| `flat_marker` | Вопросы `flat` применяются к тексту от первого маркера в пределах заданного окна. Поиск без учёта регистра по фиксированному выражению в скрипте включает «Дано», «Когда», «Если», признаки истории и проверки. При отсутствии маркера результат — `no_marker`. |

### Покрытие входа и расчёт метрик

Предел полного текста по умолчанию соответствует транспортному ограничению runtime в 64 КиБ. В этот бюджет входит также оформление запроса. Полный текст сверх выбранного байтового предела остаётся без классификации. Окно от маркера независимо измеряется в байтах UTF-8 сериализованной строки JSON с кавычками и экранированием. Для каждого переданного диапазона сохраняются полуоткрытые границы в символах Unicode, длины оригинала и отправленного входа в байтах, фактическое число входных и выходных токенов каждого успешного шага. По ID можно найти текст в зафиксированном корпусе. Сопоставляйте числа и изменившиеся решения в `view_comparison` на одних и тех же доступных ID для обоих вариантов. Записи без маркера входят в общее покрытие.

Исследованный шаблон GGUF выделяет 256 токенов на голову и допускает до 48 текстовых токенов на вариант. Закреплённый движок может сокращать вопрос и варианты, если места недостаточно. Скрипт использует однобуквенные ключи и короткие русские описания. До отправки каждого вопроса проверяется консервативная верхняя оценка по байтам UTF-8 для отформатированных вариантов, их маркеров и вопроса. Закреплённый движок GGUF сохраняет часть запроса с исходной записью целиком. При обучении multilingual checkpoint общий лимит составлял 1 024 токена. Для ответов сверх этого лимита исходные данные сохраняются в `steps` и исключаются из оценки качества и подбора порога. Разбирайте отдельно `over_budget`, `reserved_token`, `runtime_rejected` (HTTP 400/413) и `outside_training_context`. Другие ошибки runtime останавливают прогон. [Закреплённая реализация GGUF](https://github.com/ggml-org/llama.cpp/blob/b12177/tools/server/server-decision.cpp#L1269-L1321) · [Лимит запроса Ollama](https://github.com/ollama/ollama/blob/v0.40.16/server/routes.go#L948-L1027) · [Конфигурация checkpoint](https://github.com/NandhaKishorM/laya/blob/main/laya-rust/README.md#checkpoints)

Плоский и бинарный профили используют оценку выбранного варианта. Иерархический использует минимальную оценку выбранных вариантов вдоль пройденного пути. Эти числа и мера концентрации распределения отражают выход модели. Для каждой схемы и оси скрипт перебирает наблюдаемые оценки на настроечной выборке и выбирает максимальное покрытие при заданных минимуме принятых ответов и доле верных среди них. К контрольной выборке применяет тот же порог. При отсутствии подходящего порога все решения требуют проверки. В `raw_metrics` входят доступные решения до применения порога. В `metrics` учитываются и воздержания, в `accepted_accuracy` — только принятые ответы. Проверьте `accepted_errors`, `rejected_errors`, `below_threshold` и `unavailable` по ID, сравните число эталонных случаев каждого класса. Слабая оценка или отсутствие решения требует проверки человеком. Пороги исследовательской выборки автоматически в приложение не переносятся.
