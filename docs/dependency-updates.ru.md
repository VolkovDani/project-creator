# Автоматические обновления зависимостей

**English version:** [docs/dependency-updates.md](dependency-updates.md).

Репозиторий использует обновления версий Dependabot через
[`.github/dependabot.yml`](../.github/dependabot.yml). Конфигурация должна
находиться в ветке по умолчанию (`main`); каждый блок обновлений версий нацелен
на `develop`, поэтому Dependabot читает манифесты из `develop` и создаёт PR
обновлений версий для `develop`. Ветка `develop` существовала во время подготовки
конфигурации.

## Охват

| Экосистема | Настроенные каталоги | Отслеживаемые файлы |
| --- | --- | --- |
| Go modules (`gomod`) | `/` | `go.mod`, `go.sum` |
| Bun | `/frontend` | `package.json`, `bun.lock` |
| pip | `/runtime/npu` | `requirements.txt`, `requirements-export.txt` |
| Docker | `/`, `/frontend` | Корневой `Dockerfile`, корневые `Dockerfile.*` и `frontend/Dockerfile` |
| Docker Compose | `/` | Корневые файлы `compose*.yml` |
| GitHub Actions | `/` | Workflow-файлы в `.github/workflows` |

Обновляющий модуль Python поддерживает файлы зависимостей `.txt`. Модуль Docker
распознаёт имена Dockerfile, содержащие `dockerfile` (включая варианты
`Dockerfile.ollama-*` в этом репозитории); в текущем исходном коде Dependabot
используется регистронезависимый шаблон имён `dockerfile|containerfile`. Этот
охват предполагаемый и не гарантирует обновление каждого закреплённого значения.
В частности, файл export-зависимостей содержит прямую ссылку на wheel, локальные
теги образов в Compose исключены, а разбор Docker-образов имеет ограничения,
описанные ниже.

## Оценка менеджера пакетов Bun

В `frontend/package.json` закреплён Bun 1.4.4, в репозитории хранится
`frontend/bun.lock`. GitHub указывает поддержку [экосистемы Dependabot `bun`](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories) для
Bun версии 1.1.39 и новее. В [списке экосистем dependency graph](https://docs.github.com/en/code-security/reference/supply-chain-security/dependency-graph-supported-package-ecosystems)
Bun пока отсутствует. Набор имён пакетов и версий после переноса с npm не
изменился: совпали все 317 пар имени и версии, включая override
`graphql-config` → `minimatch@11.0.1`. Это сравнение не доказывает идентичную
топологию peer-зависимостей и hoisting; результат проверяется frontend-тестами,
проверкой типов, сборками и container smoke. 17 ноября 2026 года `bun audit` не
сообщил advisory в 295 пакетах Bun lockfile.

Поэтому нельзя полагаться на dependency-graph alerts для сканирования `bun.lock`;
CI и проверка выпуска запускают [`bun audit`](https://bun.sh/docs/pm/cli/audit) по
зафиксированному графу, а еженедельный/manual workflow проверяет default branch.
Bun отправляет список пакетов в npm advisory endpoint; при ошибке или неразбираемом
ответе проверка завершается ошибкой. Она не заменяет просмотр уведомлений
upstream-проектов.

Bun распространяется по [лицензии MIT](https://github.com/oven-sh/bun/blob/main/docs/project/license.mdx); на официальной странице лицензирования
также перечислены компоненты JavaScriptCore/WebKit по LGPL-2 и лицензии
встроенных библиотек. Bun используется только для управления зависимостями
фронтенда и этапа сборки Next.js. Production-образ и сервер остаются на Node.js,
поэтому исполняемый файл Bun и его библиотеки не входят в распространяемый
runtime-образ фронтенда. Решение оставить production на Node соответствует
[руководству Next.js по развёртыванию](https://nextjs.org/docs/app/guides/deploying-to-platforms),
где указан сервер Node.js.

На дату перехода Bun 1.4.4 был [последним выпуском](https://github.com/oven-sh/bun/releases/tag/bun-v1.4.4); его GitHub tag указывает на
проверенный подписанный release commit. В этой версии исправлена
[уязвимость высокого уровня HTTP/3 QPACK header amplification](https://github.com/oven-sh/bun/security/advisories/GHSA-cf8x-9m69-3gg3), затрагивавшая Bun 1.4.3 и
старше. npm проверяет целостность [platform-specific пакета](https://www.npmjs.com/package/@oven/bun-linux-x64/v/1.4.4); поля `os`/`cpu`
указывают Linux x64, но текстовое описание ошибочно называет macOS arm64.
Установленный бинарный файл сообщил Linux x64 и revision `1.4.4+38afee6c8`, что
подтверждает ограничение несоответствия только метаданными описания пакета.

Поле `trustedDependencies` задано пустым, поэтому Bun не запускает install-скрипты
сторонних зависимостей. Текущим зависимостям фронтенда эти скрипты не нужны;
frontend-тесты, проверка типов, сборки и container smoke обнаружат зависимость,
для которой они понадобятся в будущем. GitHub Actions кеширует только registry
package cache Bun по ключу из `frontend/bun.lock`; квота кеша репозитория не меняется.

На локальной Linux x64-системе с Node 24.21.0, Bun 1.4.4 и Next.js 16.4.6 медиана
трёх чистых сборок составила 4.31 секунды на Node и 3.88 секунды на Bun. Медиана
трёх сборок с кешем составила 1.98 и 1.51 секунды соответственно. Все сборки
завершились успешно. Это локальные измерения, а не гарантия на другом оборудовании.
Под Bun выполняется только `next build`; unit-тесты и production-сервер остаются
на Node.

## Сводное обновление зависимостей (2026-11-17)

Это обновление объединяет предложения по зависимостям из PR Dependabot [#112–120, #122, #133 и #134](https://github.com/VolkovDani/project-creator/issues/137). Старое предложение с npm lockfile из #121 заменено обновлениями Bun lockfile из #133 и #134; `package-lock.json` не добавлялся.

Теперь фронтенд закрепляет React 19.3.1, Biome 2.6.7, Playwright 1.65.1, типы Node 26.6.6 и TypeScript 7.0.2. Установка Bun по lockfile, форматирование, проверка типов, unit-тесты и production-сборка завершились успешно. Production-образ Node 26.13.1 также успешно собран, включая сборку Next.js и детерминированные тесты.

Версии модулей backend соответствуют #117, а образ сборки Go 1.27.4 — предложению #114. В Compose используется pgvector 0.8.7. Actions checkout и загрузка артефактов обновлены по #116 и #118. Закрепления NPU export включают NNCF 3.4.0, ONNX 1.23.2 и Optimum Intel 2.2.0.

Предложенная в #119 версия `transformers==5.23.0` не сохранена: опубликованные [метаданные Optimum Intel 2.2.0](https://pypi.org/project/optimum-intel/2.2.0/) требуют `transformers>=4.51,<5.6`. Сейчас закреплена **5.5.4** — последняя неотозванная стабильная версия в этом диапазоне по проверке от 17 ноября 2026 года. Прежняя проверка resolver приняла 5.5.2; она не подтверждала совместимость экспорта или инференса.

Чистая установка сначала выбрала PyPI `torchvision==0.29.2`: проверка зависимостей прошла, но импорт завершился ошибкой `operator torchvision::nms does not exist`. Теперь export requirements также закрепляют официальный CPU wheel `torchvision==0.29.1+cpu` для Linux x86_64 / CPython 3.12 с SHA256. Это самый новый подходящий CPU wheel, найденный в официальном индексе на дату проверки. Регрессионный тест упал до изменения и прошёл после него: проверены нативная CPU-операция NMS и импорт экспортера Optimum. Чистая установка существующих requirements из `main` на `8ff1e0e` не установила torchvision и успешно импортировала экспортер; конкретный сбой появился при обновлении зависимостей и не воспроизведён на этом срезе main.

После установки `runtime/npu/requirements-export.txt` в отдельное окружение экспорта запустите явную проверку окружения:

```bash
uv pip check --python .npu/export-env/bin/python
NPU_EXPORT_ENV_SMOKE=1 .npu/export-env/bin/python -m unittest discover -s runtime/npu -p test_export_environment.py -v
```

Обычные unit-тесты пропускают эту проверку и не устанавливают модельные библиотеки. Её успех подтверждает совместимость нативной операции и импорта, а не качество модели; экспорт и NPU-инференс требуют отдельных явных аппаратных проверок.

**Временное ограничение безопасности:** Transformers 5.5.4 остаётся затронут [GHSA-xrqw-3rrv-vx5w](https://github.com/advisories/GHSA-xrqw-3rrv-vx5w) и [GHSA-x9r9-c232-4q39](https://github.com/advisories/GHSA-x9r9-c232-4q39). 17 ноября 2026 года владелец выбрал совместимые стабильные релизы до выхода выпущенной версии Optimum Intel с поддержкой исправленного Transformers. Замена и проверка отслеживаются в [#144](https://github.com/VolkovDani/project-creator/issues/144); предупреждения не отклоняются, security PR #142 не считается заменённым. До обновления экспортируйте только проверенные локальные снимки моделей закреплённых ревизий в изолированном окружении без учётных данных и сети, с записью только в отдельный каталог результата. Эти меры снижают риск, но не исправляют уязвимости библиотеки. Окружение экспорта отделено от OpenVINO GenAI runtime приложения.

### Аппаратная проверка обновлённого экспорта (17 ноября 2026 года)

Код приложения/runtime: `bd8bdd0288a337257a7b2ef0558f434e33b8f8f4`, с указанными выше export-зависимостями. Ноутбук: Core Ultra 7 268V, Intel AI Boost, 32 ГБ RAM, Linux `7.0.0-43-generic`; Intel NPU driver/compiler/firmware `1.38.0.20260910-34487311128~ubuntu26.04`. Python 3.12.14; OpenVINO/GenAI/tokenizers 2026.4.1/2026.4.1.0/2026.4.1.0; бинарник smoke-тестов собран Go 1.27.3.

Новый офлайн-экспорт `Qwen/Qwen2.5-7B-Instruct` ревизии `a09a35458c702b33eeacc393d103063234e8bc28` использовал `text-generation-with-past`, симметричные INT4-веса, ratio 1.0, group size -1. Экспорт завершился за **44,44 секунды**, пик RSS — **18,44 ГиБ**, размер модельных файлов — около **4,1 ГиБ**. Экспортер работал с отключённой сетью, скрытыми домашними каталогами и сохранением файлов только в тестовый каталог, с лимитами памяти 20 ГиБ и swap 2 ГиБ. Исходные веса и действующая модель приложения не перезаписывались.

Новый runtime-профиль — `a31f6d86ee327e8fd8a0283868fd4a000ec8efda30e637577d37d192eff418fc` (2048 токенов входа / 512 выхода). Холодная загрузка NPU заняла **33,84 секунды**; после полного перезапуска модель загрузилась с кешем за **2,40 секунды** и прошла новое сравнение с противоречием; все **14 фиксированных сравнений пар** прошли проверки ожидаемых вердиктов и источников. Счётчик занятости NPU вырос на **111,46 секунды** за этот набор. Отмена с восстановлением worker и новой генерацией прошла за **13,21 секунды**. Первый тест отмены прерван: старый диагностический файл с владельцем root препятствовал записи lifecycle-событий; его содержимое сохранено, запись восстановлена перед успешным повтором.

Локальные подтверждения находятся в корневом `logs/npu/issue137/` (`export.log`, `smoke.log`, `cancel.log`, проверки окружения/импортов и счётчики устройства); модельные файлы, профиль и freeze зависимостей — в `.npu/issue137/`. Логи и веса не коммитятся. Фиксированные примеры подтверждают эту конфигурацию экспорта/runtime, а не общую точность модели, сравнение CPU/GPU или устранение оставшихся уязвимостей.

## Расписание и число PR

Каждая экосистема проверяется еженедельно, по очереди с понедельника по субботу.
Обновления SemVer minor и patch для каждой экосистемы объединяются в один PR;
major обновления остаются отдельными. Для каждого блока экосистемы Dependabot
может держать открытыми не более двух PR обновлений версий. При шести настроенных
блоках это ограничивает общее число открытых PR обновлений версий двенадцатью.
Для PR обновлений безопасности действует отдельное ограничение GitHub; заданный
здесь лимит обновлений версий на них не распространяется.

По умолчанию Dependabot выдерживает трёхдневную паузу перед обновлением версии;
она не задерживает обновления безопасности. Конфигурация не добавляет метку
`automerge` и не настраивает автоматическое слияние. Стандартные метки Dependabot
для зависимостей не запускают автомерж; предложенные обновления по-прежнему
требуют CI и проверки по обычным правилам репозитория.

PR Dependabot запускают существующую проверку pull request в репозитории. В
актуальной документации биллинга GitHub стандартные GitHub-hosted runners для
Dependabot указаны как бесплатные, в том числе для приватных репозиториев.
Репозиторий приватный, но общие настройки биллинга аккаунта и остаток квоты не
проверялись; это не гарантирует отсутствие платы за другие запуски Actions или
хранение данных.

## Ветки и обновления безопасности

Веткой по умолчанию остаётся `main`. Параметр `target-branch: develop` действует
на обновления версий: Dependabot читает манифесты из `develop` и направляет PR на
эту ветку. По документации GitHub, настройки `target-branch` не применяются к
обновлениям безопасности. Такие PR продолжают направляться в ветку по умолчанию
(`main`) и используют отдельные настройки и лимиты.

17 ноября 2026 года read-only запросы к GitHub API вернули HTTP 204 для endpoint
предупреждений об уязвимостях репозитория и `{ "enabled": true, "paused": false }`
для автоматических исправлений безопасности. Эти результаты подтверждают только
состояние двух endpoint на тот момент; они не устанавливают состояние всех
функций безопасности кода.

## Ограничения проверки

Dependabot обновляет манифесты, но не заменяет проверку совместимости и CI. По
документации GitHub, обновление Dockerfile может затронуть только первую
инструкцию `FROM`, а ссылки на образы в инструкциях `ARG` не обновляются. Во
`frontend/Dockerfile` один закреплённый образ Node используется и на этапе сборки,
и на этапе запуска, поэтому нужно проверять, что предложенное обновление сохраняет
одинаковую версию в обоих этапах. Также проверяйте изменения Docker-образов и
Compose. Для локально собранных образов `project-creator-ollama-intel` и
`project-creator-ollama-amd-vulkan` нет внешнего источника версий, поэтому Compose
updater их игнорирует.

Перед слиянием изучайте примечания к выпуску каждого изменения и запускайте
подходящие проверки репозитория. Не принимайте major обновление только потому,
что его предложил Dependabot.
