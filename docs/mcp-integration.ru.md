# Подключение ассистента через MCP

[English version](mcp-integration.md)

MCP-клиент может читать активные требования одного проекта Project Creator,
анализировать их выбранной моделью и сохранять предложения для проверки
человеком. Откройте **Анализ → Внешние предложения**, чтобы увидеть выводы,
ограничения и версии источников. Вносите правки отдельно через
**Требования**. [Задача #146](https://github.com/VolkovDani/project-creator/issues/146)

## Подключение клиента

Обновите [локальную установку](ai-installation.ru.md) и запустите бэкенд и
веб-интерфейс. Откройте проект в браузере и скопируйте ID из `/projects/<id>`.
Добавьте в клиенте отдельную запись для каждого проекта, которым хотите поделиться.

Выберите `--sharing=local` для клиента, который использует только локальную
модель. Указывайте `--sharing=cloud`, только если согласны передать содержимое
проекта внешнему провайдеру клиента. В обоих режимах клиент получает доступ к
активным требованиям и сохранённым предложениям выбранного проекта. Настройка
фиксирует ваш выбор. Перед подключением проверьте у клиента провайдера,
хранение данных и условия переключения на другие модели. Сам адаптер Project
Creator не вызывает модели.

В примерах используется Docker Compose. Укажите каталог проекта, имя проекта
Compose и набор файлов работающей установки. Передавайте нужные глобальные
параметры Compose перед `exec`. Подпроцесс получает токен workspace из
окружения бэкенда внутри контейнера.

### Локальная модель в OpenCode

В OpenCode 1.19.6 добавьте запись в `opencode.json`. Настройте в OpenCode
локальный провайдер, например Ollama, и выберите его модель.

```json
{
  "mcp": {
    "project_creator": {
      "type": "local",
      "command": ["docker", "compose", "--project-directory", "/absolute/path/to/project-creator",
        "exec", "-T", "backend", "/app/server", "mcp", "--project=PROJECT_ID", "--sharing=local"],
      "enabled": true
    }
  }
}
```

Проверьте подключение командой `opencode mcp list`. Инструменты сервера
доступны выбранной локальной модели.
[OpenCode 1.19.6](https://github.com/anomalyco/opencode/releases/tag/v1.19.6) · [Настройка Ollama](https://opencode.ai/docs/providers/#ollama)

### Codex CLI с подпиской ChatGPT

Используйте аккаунт ChatGPT с доступом к Codex CLI. Добавьте сервер
в `config.toml` Codex и перезапустите CLI.

```toml
[mcp_servers.project_creator]
command = "docker"
args = [
  "compose", "--project-directory", "/absolute/path/to/project-creator",
  "exec", "-T", "backend", "/app/server", "mcp",
  "--project=PROJECT_ID", "--sharing=cloud"
]
```

Для проверки попросите клиента перечислить требования в проекте с тестовыми
данными. Проверьте результат и попросите сохранить предложение со ссылками на
прочитанные ID и версии. Откройте предложение в Project Creator.
[Настройка MCP в Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) · [Доступ к Codex по подписке](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)

### Бэкенд запущен на хосте

Если бэкенд работает напрямую на хосте, замените `docker compose … exec -T
backend /app/server` абсолютным путём к бинарнику, собранному из `./cmd/server`.
Передайте тот же токен workspace в приватной переменной
`PROJECT_CREATOR_TOKEN` подпроцесса и укажите порт из `PROJECT_CREATOR_ADDR`,
если он отличается от 8080. Храните токен вне аргументов команд,
общедоступных конфигураций и логов.

## Инструменты и просмотр предложений

- `list_requirements` возвращает ID, актуальные версии и текст активных
  требований. Для продолжения используйте курсор из результата.
- `list_similar_requirement_pairs` читает уникальные пары активных требований
  с рассчитанным косинусным сходством от заданного порога. Для каждой пары
  возвращаются оба исходных текста, ID, версии, балл и `glossaryContext` с
  подтверждёнными определениями, найденными в любом из исходников.
  Неоднозначные варианты помечаются для уточнения. Страница указывает
  профиль эмбеддингов, использованный для расчёта.
- `save_external_proposal` сохраняет анализ, ограничения, сведения о клиенте
  и модели, режим передачи данных и от 1 до 20 версий разных требований.
  В `glossarySources` можно указать до 20 разных понятий с `termId` и версией.
  При сохранении обе группы ссылок проверяются в рамках проекта. В черновике
  видно, если понятие изменилось или удалено.
  Идентификатор модели передаёт клиент. Идентификатор клиента берётся из
  заявленных им данных MCP. Если указанное требование изменилось или стало
  недоступным до сохранения, обновите данные и проанализируйте актуальный
  текст. При сбое связи повторите запрос с тем же ID и содержимым.
- `list_external_proposals` возвращает сохранённые черновики и актуальность
  источников, с пагинацией по курсору. Источник **актуален**, пока совпадает
  его активная версия, **изменён**, если появилась новая активная версия, и
  **недоступен** после архивации или удаления. ID и версия остаются видимыми.

Предложение получает статус **Ожидает проверки**. Прежде чем вносить правку,
проверьте обоснование и версии источников. Адаптер предоставляет актуальные
тексты требований, отобранные по косинусному сходству пары и предложения.
История текстов, другие типы источников, изменение требований через MCP
и удалённый MCP-сервер вне текущего объёма.

## Сравнение пар требований в чате

Например, попросите подключённого ассистента вызвать
`list_similar_requirement_pairs` с `threshold: 0.8`, сравнить найденные пары
на совпадения или противоречия и привести ID и версии обоих источников
вместе с использованными определениями.
Балл равен максимальному косинусному сходству между индексированными
фрагментами актуальных версий двух требований. Даже одинаковые тексты должны
набрать запрошенный балл. Сходства и различия интерпретирует сам ассистент.
По вашему запросу он может сохранить выводы через `save_external_proposal`.

Пока `hasNextPage` равно true, передавайте тот же порог и возвращённый
`pageInfo.endCursor`. Инструмент просматривает ограниченные группы пар,
поэтому попадаются пустые страницы с продолжением. Если требования, профиль,
индекс или глоссарий изменились, после `cursor_stale` начните с первой страницы.
При неполном индексе дождитесь завершения индексации активных требований
и повторите запрос. Инструмент читает готовые эмбеддинги и возвращает
`embeddings_not_configured`, если активного профиля нет.

## Архитектура и проверка

Локальный stdio работает через официальный Go SDK без публичной точки входа
и отдельного сетевого сервиса. Подпроцесс вызывает фиксированные
операции GraphQL по IPv4 loopback с существующим токеном workspace.
Аргументы запуска ограничивают его одним проектом. Бэкенд проверяет workspace
и проект при каждом чтении и записи. Настраивать подпроцесс и предоставлять
доступ к Docker должен владелец устройства.

PostgreSQL хранит предложения отдельно от требований. В одной транзакции
проверяются активные версии источников и записываются черновик и событие
инвалидации. ID запроса действует в пределах проекта, что исключает дубликат
при повторе. Страница просмотра определяет актуальность по текущим
источникам. Черновик может содержать цитаты и остаётся доступным после
удаления источника.

Детерминированные интеграционные тесты покрывают инструменты MCP, GraphQL,
PostgreSQL и просмотр в браузере. Тесты отбора пар проверяют включение
граничного балла, область доступа и продолжение с пустых страниц. В отдельном
стеке Compose первые три инструмента проверены через `docker compose exec -T`.
Codex CLI 0.172.0 и OpenCode 1.19.6 обнаружили и вызвали эти инструменты через
stdio с бинарником Project Creator и синтетическими данными GraphQL. Codex вызывал инструменты напрямую.
OpenCode использовал заглушку модели на loopback. Работа подписочной модели
и генерация через Ollama в этих проверках остались непроверенными.
