# Аппаратная приёмка выпуска v0.1.0

English version: [release-acceptance.md](release-acceptance.md).

Успешный CI подтверждает прохождение детерминированных тестов и сборок
контейнеров. Он не подтверждает работу реального профиля модели на целевом
устройстве. Оставляйте prerelease v0.1.0 черновиком, пока maintainer не проверит
отчёты с реального оборудования.

## Отчёт для каждой комбинации оборудования и профиля

Используйте шаблон issue **Hardware release acceptance**. Приложите полные
логи и укажите:

- тег кандидата и полный SHA исходного коммита;
- отдельные точные строки в теле issue: `release-tag: v0.1.0` и
  `source-sha: <полный SHA из 40 символов>`; это связывает решение maintainer с
  конкретным кандидатом;
- модели CPU, GPU/NPU и идентификаторы устройств, объём памяти, ОС, версии ядра,
  драйверов и runtime;
- версии Compose и приложения, Ollama/runtime, имя и digest модели, ID профиля
  и хеш его конфигурации;
- точные команды smoke и результат каждого сценария: запуск, типовая генерация,
  рестарт/восстановление и чистое завершение; по возможности — время и ресурсы;
- полные исходные логи без секретов и персональных данных;
- при наличии — ссылки на независимые отчёты, сгруппированные по патчу выпуска,
  с перечислением подтверждённых сочетаний устройств/профилей и результатов;
  отдельное независимое воспроизведение не является обязательным для первичного
  отчёта;
- пользовательские исправления, совместимость и известные ограничения.

## Операционные проверки

Выполните на кандидате и приложите команды, результаты и логи:

1. Запустите чистую копию по инструкции установки в README с новым `.env`;
   запишите версии образов, приложения, БД, runtime и модели.
2. Проверьте digest модели и настройки профиля. На проекте с типовыми
   требованиями выполните генерацию для известного конфликта и совместимой
   пары; проверьте источники и происхождение результата.
3. Перезапустите Compose и проверьте сохранность данных, подключение модели и
   восстановление анализа. Выполните backup/restore командами из README.
4. Перед обновлением существующей установки создайте резервную копию. Выполните
   обновление с предыдущей поддерживаемой версии, сохраните вывод миграций и
   проверьте доступность прежних проектов и требований.
5. Запишите корректное завершение работы и использование ресурсов; при сбоях
   сохраните полную диагностику.

## Решение о приёмке и подготовке черновика

Maintainer проверяет отчёт, привязку к версии и SHA, логи, идентификаторы и
результаты. Независимый прогон сообщества для первичной приёмки не требуется.
После явного решения maintainer применяет метку `hardware-accepted` и закрывает
issue. Ручной workflow выпуска требует закрытую issue с этой меткой, тег версии,
полный SHA, успешный CI на том же SHA и его присутствие в `main`; затем он
повторяет проверки этого коммита и создаёт только черновик GitHub prerelease.
Метка отражает человеческое решение, её нельзя заменить успешным CI или
самооценкой модели.

Для первого выпуска Source + Compose используйте `v0.1.0`. Публикация черновика
остаётся отдельным ручным действием maintainer после проверки release notes и
оставшихся аппаратных/установочных условий. Не публикуйте выпуск, пока любая
обязательная приёмка профиля остаётся открытой.

Группируйте ссылки на независимые отчёты по патчам выпуска. Не переносите
результат одного устройства на все модели производителя. В release notes
перечислите проверенные сочетания и явно укажите непроверенные.
