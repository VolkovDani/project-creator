# Приёмка выпуска v0.1.0 и аппаратные отчёты

English version: [release-acceptance.md](release-acceptance.md).

Первый prerelease MVP v0.1.0 можно опубликовать после прохождения release
workflow, если нет известных критических проблем. Аппаратные отчёты по профилям
остаются полезными свидетельствами, которые следует собирать и проверять после
публикации; они не являются условием публикации v0.1.0. Не описывайте
непроверенное устройство или профиль как проверенные.

## Отчёты по оборудованию и профилям

Используйте шаблон issue **Hardware release acceptance** для каждой комбинации
оборудования и профиля. Приложите полные логи и укажите:

- тег кандидата и полный SHA исходного коммита;
- отдельные точные строки в теле issue: `release-tag: v0.1.0` и
  `source-sha: <полный SHA из 40 символов>`; они привязывают отчёт к выпуску;
- модели CPU, GPU/NPU и идентификаторы устройств, объём памяти, ОС, версии ядра,
  драйверов и runtime;
- версии Compose и приложения, Ollama/runtime, имя и digest модели, ID профиля
  и хеш его конфигурации;
- точные команды smoke и результат каждого сценария: запуск, типовая генерация,
  рестарт/восстановление и чистое завершение; по возможности — время и ресурсы;
- полные исходные логи без секретов и персональных данных;
- при наличии — ссылки на независимые отчёты, сгруппированные по патчу выпуска,
  с перечислением подтверждённых сочетаний устройств/профилей и результатов;
- пользовательские исправления, совместимость и известные ограничения.

Maintainer может проверить отчёт и зафиксировать явное решение меткой
`hardware-accepted`. Метка отражает проверенные человеком свидетельства, но не
блокирует публикацию v0.1.0. Результат CI и самооценка модели не заменяют
аппаратные свидетельства. Отчёт относится только к указанным устройству и
профилю.

Рекомендуемые операционные проверки для отчётов:

1. Начните с чистой копии и выполните инструкции установки из README с новым
   `.env`; запишите версии образов, приложения, БД, runtime и модели.
2. Проверьте digest модели и настройки профиля. На проекте с типовыми
   требованиями выполните smoke для известного конфликта и совместимой пары;
   проверьте источники и происхождение результата.
3. Перезапустите Compose и проверьте сохранность данных, подключение модели и
   восстановление анализа. Выполните backup/restore командами из README.
4. Перед обновлением существующей установки создайте резервную копию. Выполните
   обновление с предыдущей поддерживаемой версии, сохраните вывод миграций и
   проверьте доступность прежних проектов и требований.
5. Запишите корректное завершение работы и использование ресурсов; при сбоях
   сохраните полную диагностику.

## Подготовка и публикация v0.1.0

Ручной release workflow запускается только dispatch-событием из `main`. Он
принимает тег semantic version и полный source SHA, проверяет, что тег указывает
ровно на этот SHA, SHA достижим из `main`, а успешный CI на `main` завершился на
том же SHA. Для первого prerelease MVP Source + Compose используйте `v0.1.0`.
Workflow повторяет проверки и сборки на source SHA и создаёт **черновик
prerelease**. Maintainer проверяет кандидата и release notes, убеждается, что
нет известных критических проблем, и отдельно публикует prerelease. Аппаратная
приёмка не является условием публикации; нерешённые проблемы установки или
документации можно исправить в patch-релизах.

## Подтверждения сообщества по патчам выпуска

Группируйте независимые отчёты по подтверждаемому patch-релизу. По возможности
указывайте логи, версии, идентификаторы и результаты. Не переносите результат
одного устройства на все модели производителя. В release notes перечисляйте
проверенные сочетания и явно отмечайте непроверенные.
