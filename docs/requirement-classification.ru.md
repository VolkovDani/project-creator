# Классификация записей требований

[English version](requirement-classification.md)

Версия правил 2 добавляет `test_case` на ось формы. Смысл и форма независимы. Составная или неоднозначная запись может получить unknown по одной оси и известный тип по другой. Текст сохраняется целиком.

| Код | Определение | Пример | Контрпример |
| --- | --- | --- | --- |
| `business_requirement` | Цель бизнеса | Сократить ожидание вдвое | Показать очередь |
| `stakeholder_requirement` | Потребность участника | Диспетчеру нужно видеть срочные заказы | Записать время |
| `functional_requirement` | Действие системы | Сохранить интервал | Закончить перенос к маю |
| `non_functional_requirement` | Характеристика качества | Отвечать за секунду | Отправить квитанцию |
| `transition_requirement` | Временная потребность перехода | До запуска перенести заказы | Постоянно хранить историю |
| `business_rule` | Правило предметной области | Скидка доступна только участникам | Вывести сумму жирным |
| `constraint` | Заданное ограничение реализации | Использовать существующую локальную БД | Сократить ожидание |
| `statement` | Утверждение или предписание | Сохранить интервал | Дано … когда … тогда … |
| `user_story` | Роль, потребность и цель | Как оператор я хочу видеть очередь для выбора заявки | Система выгружает файл |
| `use_case` | Цель участника и поток с возможными альтернативами | Подать заявку, проверить, принять или вернуть | Заявка ожидает |
| `scenario` | Конкретная последовательность в контексте | Диспетчер закрывает пустую очередь, открывает её снова и видит ноль заявок | Отвечать за секунду |
| `acceptance_criterion` | Проверяемое условие приёмки | При повторном открытии пустой очереди должно отображаться ноль заявок | Повысить удобство |
| `test_case` | Воспроизводимая проверка с начальными условиями или тестовыми данными, шагами и ожидаемым результатом | Подготовьте очередь A без заявок. Закройте и снова откройте очередь A. Проверьте, что счётчик заявок равен 0. | При повторном открытии пустой очереди должно отображаться ноль заявок |
| `other` | Распознаваемое содержание вне категорий | Заметка о встрече (смысловая ось) | Неясный фрагмент |
| `unknown` | Недостаточно оснований для одной метки | Быстрее (объект не указан) | Явно заданная выгрузка |

Три примера с пустой очередью описывают одно и то же поведение системы (`functional_requirement`). Сценарий описывает действия диспетчера и то, что он видит. Критерий приёмки задаёт условие, по которому принимают это поведение. Тест-кейс объясняет, как воспроизвести и проверить его.

При новом ручном подтверждении сохраняется версия правил 2. История предыдущих решений сохраняет исходные метки и версию правил.

Исходное состояние существующих записей — `unclassified`. Операция `confirmRequirementClassification` требует версии текста и текущей ревизии решения. Изменение текста переводит предыдущее решение в `stale`; история сохраняет его исходный статус. Поиск с фильтрами возвращает типы последней ревизии вместе с её статусом. Состояние выполняемой классификации в API и интерфейсе — `classifying`. Оценки альтернатив принадлежат модели. Автоматическая классификация зависит от benchmark #50.
