# Установка и запуск через CLI

Из корня клонированного репозитория:

```bash
./project-creator setup --device cpu
# либо Intel Arc:
./project-creator setup --device arc
# либо NVIDIA GPU / совместимая AMD dGPU или iGPU:
./project-creator setup --device nvidia
./project-creator setup --device amd
# либо Intel NPU для генерации + CPU для BGE-M3:
./project-creator setup --device npu
# либо Intel NPU для генерации + Intel Arc для Ollama (embeddings):
./project-creator setup --device npu --ollama-device arc --gpu-id 0
```

`setup` — явное разрешение загрузить локальные веса, контейнеры и необходимые
NPU-зависимости. Команда подготавливает конфигурацию, загружает и закрепляет
модели, при необходимости экспортирует Qwen, запускает runtime и Compose,
проверяет интерфейс/API, индексацию и реальный анализ трёх синтетических пар.
При успехе печатает URL приложения. Создавать `.env`, вручную копировать digests,
экспортировать веса или запускать второй терминал не требуется.

```bash
./project-creator up       # повторный запуск и полная AI-проверка
./project-creator doctor   # диагностика без загрузки моделей
./project-creator down     # остановка с сохранением всех томов/весов
./project-creator --lang en doctor
```

`up` использует подготовленные веса; не вызывает `ollama pull`, snapshot download,
`pip install` или exporter. Сборка контейнеров может обращаться к реестрам и
репозиториям зависимостей. `doctor` проверяет окружение, доступность UI/API и pins
установленных моделей; он не запускает inference и не утверждает качество модели.
Контейнер диагностического инструмента запускается с `--pull never`.

## Системные prerequisites

Первая поддерживаемая матрица — **нативный Linux x86_64, Python 3.12,
Docker Engine и Docker Compose v2.20+**. Docker Desktop, Windows, macOS,
ARM и автоматическая настройка rootless NPU socket mapping не входят в неё.
Подсказки, этапы и объяснения стабильных кодов ошибок CLI доступны на русском
и английском (`--lang en`). Исходная техническая диагностика Docker, Python,
Ollama и других инструментов сохраняется на их языке (обычно английском)
и явно помечается отдельно от локализованного объяснения и следующего действия.

CLI поставляется исходным исполняемым файлом в репозитории, без сторонних
Python-зависимостей для CPU/GPU. Запускайте его от обычного пользователя,
имеющего доступ к Docker Engine; не запускайте установщик через `sudo`.

Установите Docker по официальной инструкции, запустите Engine и убедитесь,
что `docker info` и `docker compose version` работают для текущего пользователя.
Установка драйверов, изменение групп/прав и перезагрузка выполняются отдельно,
не скрываются внутри `setup`.

| Режим | Проверки и подготовка |
| --- | --- |
| CPU | RAM не менее 8 GiB, RAM+swap не менее 12 GiB, свободный диск от 24 GiB перед первой установкой. Для Qwen 7B рекомендуется 16–32 GB RAM. |
| Arc | Те же ресурсы, Intel render device в `/dev/dri`, права чтения/записи; Linux graphics/Vulkan по [инструкции Arc](intel-arc.md). |
| NVIDIA | Те же ресурсы, совместимая GPU и NVIDIA-драйвер, настроенный NVIDIA Container Toolkit в Docker и `nvidia-smi` на хосте. |
| AMD | Те же ресурсы, совместимый ROCm 7 driver, `rocminfo` на хосте, доступ к `/dev/kfd` и `/dev/dri`. Только GFX targets из закреплённой upstream-матрицы. |
| NPU | RAM от 20 GiB, RAM+swap от 28 GiB, свободный диск от 50 GiB для исходных Safetensors, промежуточного экспорта, INT4 и кешей. Загруженный `intel_vpu`, доступный `/dev/accel/accel*`, firmware/userspace driver по [инструкции NPU](intel-npu.md). |

После подготовки требуется как минимум 6 GiB свободного диска для CPU/Arc
или 8 GiB для NPU; это бюджет запуска, а не обещание максимального расхода.
Фактический расход зависит от Docker build cache, весов и компиляции.
CLI проверяет обнаружение устройства отдельно от фактического inference.

Для NPU нужны Python 3.12 с `venv`/`pip` либо заранее установленный `uv`.
Если `python3.12` отсутствует, CLI явно скачивает через `uv` локальный
CPython **3.12.14** в `.npu/python`, не заменяя системный Python.
Runtime и exporter получают отдельные venv с версиями из
`runtime/npu/requirements*.txt`. Существующий venv без `pip` (например, созданный
через `uv venv`) дополняется через локальный `ensurepip` перед установкой
зависимостей, без пересоздания окружения. Отчёты установки сохраняются в
`logs/npu/export-env-install.json` и `logs/npu/runtime-env-install.json`,
а `pip freeze` — в `.npu/` вместе с происхождением модели;
телеметрия OpenVINO и неявная авторизация Hugging Face отключаются.
Окружение проверяет `ov.Core().available_devices` до скачивания исходных весов.

## Существующая установка и сохранение данных

Перед первым `setup` выполняйте команду из того же каталога репозитория,
с прежним `.env` и именем Compose-проекта. Если раньше использовался `-p`,
укажите это имя **на первом запуске CLI**:

```bash
./project-creator setup --device arc --project-name existing-project-name
```

Приоритет имени: явный параметр → `COMPOSE_PROJECT_NAME` окружения → значение
в `.env` → имя каталога. Имя записывается в `.env` и `.project-creator/state.json`;
после этого CLI отклоняет его случайную смену. Использование другого имени
создаёт другой namespace томов Docker, поэтому не угадывайте имя старой установки.
Произвольные Compose override-файлы из `COMPOSE_FILE` окружения не наследуются.
CLI использует только штатные `compose.yml` и выбранный override устройства.

Существующие секреты и настройки сохраняются; недостающие пароль БД и token
генерируются независимо (`secrets.token_hex(24)`). `.env` и state записываются
атомарно с правами 600. Placeholder-секреты отклоняются без автоматической
замены: так существующая БД не теряет пароль. Пароль должен быть URL-safe,
поскольку штатный Compose подставляет его в connection URL. Поддерживается
обычный literal `.env`; сложная shell-интерполяция, многострочные значения и
дублирующиеся ключи требуют предварительного упрощения вручную.
Секреты не печатаются; не публикуйте `.env`, runtime logs и install reports.

Логи и диагностические отчёты находятся в корневом `logs/`, исключённом из
Git и Docker build context. CLI создаёт `logs/npu/` для NPU runtime и отчётов
установки; stdout/stderr runtime дописываются в `logs/npu/runtime.log`.
Веса, профили и freeze окружений остаются в `.npu/`.
Логи контейнеров хранятся в Docker. При необходимости сохраните их отдельно:

```bash
mkdir -p logs
docker compose logs --no-color > logs/compose.log
```

При ручном запуске используйте те же Compose-файлы и имя проекта, что при
запуске приложения.

Ни одна команда CLI не использует `down --volumes`, не удаляет БД и не выполняет
автоматическую миграцию между разными именами проектов. `down` останавливает
Compose и только подтверждённый управляемый CLI NPU runtime. Веса, source cache,
compiled cache, manifest, история анализов и synthetic diagnostic projects остаются.
Параллельные `setup/up/down` блокируются локальным lock.

Явное переключение устройства:

```bash
./project-creator setup --device cpu --switch-device
```

При переходе с NPU управляемый runtime останавливается. Весов NPU это не удаляет.
Перехода на CPU/Arc/облако при ошибке NPU нет. По умолчанию NPU-профиль
использует CPU для Ollama и embeddings. Для Intel NPU генерации вместе с Intel
Arc для Ollama задайте `--ollama-device arc`; `--gpu-id` выбирает Vulkan ID Arc
из логов Ollama и используется тем же способом, что в обычном Arc-профиле. CLI
поднимает `compose.intel.yml` перед `compose.npu.yml`, сохраняя NPU runtime
генератора. Установка сохраняет оба устройства отдельно в приватном
`.project-creator/state.json`; повторные `up` и `setup --device npu` сохраняют
выбранный Ollama-профиль. Его смена требует явного `--switch-device`. Старые
state-файлы без `ollama_device` продолжают означать NPU-генерацию с CPU Ollama.
Проверка embeddings подтверждает Ollama offload; проверка генератора по-прежнему
подтверждает профиль NPU. Закреплённые модели, их digests и данные установки
при переключении сохраняются.

## GPU и выбор адаптера

`arc` означает GPU, включая встроенную Intel Arc; `npu` — отдельный
OpenVINO-генератор. NVIDIA использует CUDA, AMD — ROCm. Один CLI-профиль
подключает ровно один override; сочетать разные GPU overrides не нужно.

```bash
nvidia-smi -L
./project-creator setup --device nvidia --gpu-id GPU-полный-uuid
rocminfo
./project-creator setup --device amd --gpu-id GPU-полный-uuid
# Intel: числовой Vulkan ID из логов Ollama, не номер renderD*:
./project-creator setup --device arc --gpu-id 0
./project-creator setup --device cpu --switch-device
```

Это примеры: замените UUID фактическим значением утилиты. При одной NVIDIA/AMD
GPU CLI выбирает её автоматически; при нескольких требует `--gpu-id`.
NVIDIA принимает индекс `nvidia-smi` или UUID, затем сохраняет UUID. Для AMD
используйте `Uuid: GPU-...` из `rocminfo`; допустимый числовой индекс CLI —
порядок GPU начиная с нуля, без CPU agents, **не** `Agent N` из вывода.
Предпочтителен UUID. Выбранная AMD GPU должна входить в GFX-матрицу из README;
чужой или неподдерживаемый адаптер отклоняется до скачивания моделей.

NVIDIA Container Toolkit предварительно настраивается по
[официальной инструкции](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html).
CLI проверяет наличие NVIDIA runtime в Docker и драйвера 550+; некоторые старые
карты требуют 570+. Совместимость самой карты проверяйте по
[документации закреплённой версии Ollama](https://github.com/ollama/ollama/blob/v0.40.11/docs/gpu.mdx).
AMD требует [ROCm 7 Linux driver](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/)
и `rocminfo`; используется официальный образ `ollama/ollama:0.40.11-rocm`.
Системные драйверы CLI не устанавливает. Поддержка AMD ограничена upstream
GFX-матрицей: проект не проводил аппаратную приёмку AMD/NVIDIA на этой версии CLI.

Intel-профиль загружает только Intel Mesa ICD: AMD и NVIDIA Vulkan-драйверы
не участвуют в обнаружении. При нескольких Intel render devices явно задайте
ID из логов **этого** контейнера; порядок может измениться после обновления
драйвера или оборудования. Неверный индекс должен приводить к ошибке offload.
Для первоначального получения логов используйте ручной Arc-запуск по
`docs/intel-arc.md`. `--gpu-id` принимает только один адаптер, не список.
Для CPU/NPU этот параметр запрещён.

UUID/индекс сохраняется в `.project-creator/state.json`; для его смены нужен
`setup --switch-device`. Для существующего Arc state без нового поля сохраняется
старый `GGML_VK_VISIBLE_DEVICES` из `.env` (один ID либо автоматический выбор).
Сохранённый выбор имеет приоритет над `.env` и переменными shell, в том числе
при `up`, `down`, `doctor`. CUDA/ROCr/HIP/HSA overrides из shell не наследуются.
Секреты, имя Compose-проекта, БД и weights при смене GPU не заменяются.

`setup`/`up` выполняют прежние три синтетических AI-сценария. После embedding
probe и генерации проверяются загруженные model/digest и положительный
`size_vram`. В диагностике роли перечислены отдельно, с запрошенным адаптером
и байтами модели/VRAM. Положительный `size_vram` подтверждает offload, но
не измеряет долю операций и не доказывает полный GPU-режим; возможен частичный
offload на CPU. Идентичность устройства ограничена изоляцией/выбором runtime,
не выводится из значения VRAM. Автоматический CPU fallback не принимается как
успешная установка. Ошибка драйвера/модели не меняет выбранный профиль.

`doctor` читает inventory, pins и `/api/ps`, не запускает inference. Для уже
загруженной модели выводит измерение; для выгруженной — явно сообщает, что
свежая проверка требуется через `up`. `doctor --device` не может переобозначить
устройство существующей установки — переключение делается через `setup`.

Ручной AMD-запуск после настройки `.env` и загрузки/pin моделей:

```bash
PROJECT_CREATOR_GPU_ID=GPU-полный-uuid docker compose -f compose.yml -f compose.amd.yml up -d --wait
```

При ручном запуске сохраняйте те же `-f` и UUID для следующих команд.
Для NVIDIA доступен прежний `compose.gpu.yml` (без UUID выбирается индекс 0).

Аппаратная приёмка выполняется отдельно: запишите GPU/iGPU, ОС, kernel,
driver, версию runtime, UUID/индекс, digests моделей, результат `setup`/`up`,
измерения обеих ролей и три результата анализа с источниками. Проверьте
повторный `up` и явное переключение CPU↔GPU с сохранением проектов и моделей.
Тесты без GPU проверяют логику и Compose-конфигурацию, а не эти измерения.

## Закрепление моделей и повтор после прерывания

Ollama: BGE-M3 `bge-m3:567m` (1024 измерения) и Qwen `qwen2.5:7b`.
Если соответствующие MODEL/DIGEST уже заданы в `.env`, CLI сохраняет этот выбор.
Сначала проверяется локальный кеш; при отсутствии модель явно загружается
через `ollama pull` с обычным прогрессом Ollama. Полный `sha256:` digest,
происхождение, metadata и возвращённая лицензия сохраняются в state.
Повторное скачивание завершённой модели не выполняется. Смена содержимого
тега при существующем pin даёт `MODEL_DRIFT`; pin не переписывается молча.
Ollama проверяет content-addressed blobs при загрузке, backend дополнительно
проверяет модель/digest до и после запросов.
CLI принимает полную SHA256 из API как с префиксом `sha256:`, так и без него,
сохраняет pin с префиксом и сравнивает оба представления одинаково.
Короткие ID из `ollama list` для закрепления не подходят.

NPU: официальный `Qwen/Qwen2.5-7B-Instruct` (Apache-2.0), без `trust_remote_code`.
Source revision разрешается один раз в immutable commit **до** скачивания и
сохраняется в `.npu/source-revision.txt`. SDK Hugging Face переиспользует
завершённые/частично загруженные файлы своего кеша и показывает прогресс.
Safetensors сверяются с SHA256 из LFS metadata закреплённого commit;
SHA256 всех разрешённых файлов записываются в `.npu/source.json` и повторно
проверяются при использовании готового source snapshot. Лицензия копируется
в экспорт. Существующий revision из ручной инструкции сохраняется.

Экспорт выполняется офлайн с явным `--task text-generation-with-past`,
симметричным INT4, ratio 1.0, group-size -1. `TMPDIR` направлен на диск
`.npu/export-tmp`, а не на tmpfs `/tmp`. Незаконченный экспорт сохраняется в
отдельном `.partial` каталоге; повтор удаляет только этот неполный output,
сохраняя исходные веса. Завершённый экспорт с CLI completion marker может
восстановить прерванное создание manifest без повторного экспорта.

Готовые `.npu/models/qwen2.5-7b-int4`, `profile.json` и `profile.sha256`
из ручной установки используются без скачивания исходников и подготовки
exporter. Runtime проверяет hashes всех файлов по существующему манифесту.
Если старый runtime запущен вручную, сначала остановите его: CLI не захватывает
чужой сокет и не завершает процесс без подтверждённого managed PID.

При прерывании повторите ту же `setup --device ...`. Не удаляйте `.npu`,
`.project-creator`, `.env` или volumes. Если экспорт существовал до CLI, но у него
нет manifest и CLI completion marker, сохраните его и создайте manifest по
`docs/intel-npu.md`; CLI не заменяет такие веса автоматически.
Для повреждённого кеша/manifest сначала изучите конкретную ошибку; сохранённый
pin не обновляется сам при повреждении. Полное автоматическое обновление моделей
на новые версии в эту первую версию не входит.

## Проверка результата

Успех выдаётся только после ответа UI/API и полного пути через frontend proxy:
три синтетических проекта → по два требования → индексация → анализ.
Проверяются известная коллизия, совместимые требования и недостаток условий,
точные ID/версии/текст источников, объяснение и ожидаемый вердикт.
Инструкция генератору требует сначала объяснить обязанности и недостающие
критерии, затем выбрать вердикт; неопределённые условия не считаются
доказательством совместимости. Текст инструкции входит в профиль генератора
Ollama/NPU: после её обновления прежний анализ становится устаревшим,
его нужно запустить заново. Профиль весов NPU при этом не меняется.
Адаптер NPU упорядочивает пару по тексту (сравнение строк), затем передаёт
модели тексты с короткими ссылками `left/right` и
фиксированными техническими версиями. После строгой проверки ответа он
восстанавливает исходные ID/версии из проверенной пары и проверяет результат
повторно. UUID и счётчики версий не должны влиять на смысловой вывод модели;
неизвестные ссылки и неверные версии отклоняются до восстановления.
Перестановка двух требований даёт модели тот же запрос; результат возвращается
с ID/версиями в исходном порядке. Позиционные слова в сгенерированном объяснении
могут относиться к порядку модели; проверяйте смысл по текстам обоих источников.
Диагностические проекты имеют имя `Installation diagnostic: ... [marker]`,
создаются явно этой командой и сохраняются в приложении. Повтор использует
свои проекты, не меняет тексты существующих клиентских требований и не удаляет
ручные изменения в диагностическом проекте. При изменении диагностических
требований проверка останавливается с `FIXTURE_CHANGED`.

Анализ запускается асинхронно. CLI и Compose smoke ожидают завершения той же
попытки через `projectAnalysis`, не создавая новую при каждом опросе, и проверяют
ID и снимки источников. Ожидание ограничено45 минутами; при истечении времени
сохранённый прогресс остаётся в проекте. Успех `setup`/`up` по-прежнему требует
завершённого анализа с ожидаемыми выводами, а не только состояния `running`.

Здоровый контейнер и найденный `accel0` сами по себе не считаются успехом.
Для Ollama выполняется отдельный embedding probe (1024 finite nonzero values),
проверяется loaded digest и `size_vram` после inference: CPU — 0, Arc/NVIDIA/AMD — больше 0.
Это подтверждает GPU offload, но не обещает полного GPU выполнения всех операций.
Для NPU подтверждается `device=NPU` и точный профиль native runtime; runtime
выбирает только NPU, без AUTO. При неверном JSON, источниках, вердикте или устройстве
команда завершается ненулевым кодом и сохраняет `verified=false`.

Качество модели не исправляется установщиком. Если NPU отвечает корректным JSON,
но ошибается на одном из примеров, `MODEL_QUALITY` остаётся ошибкой; приложение
может быть доступно для ручной диагностики. Такой результат не скрывается
заявлением об успешной установке. Три примера — проверка проводки и короткая
приёмка модели, а не статистическая оценка качества RAG.

| Код | Что проверить |
| --- | --- |
| `PLATFORM`, `DOCKER`, `RESOURCES` | Поддерживаемая ОС, Engine/Compose, RAM/swap/диск. |
| `DEVICE_ACCESS`, `DEVICE_DRIVER`, `DEVICE_EXECUTION` | Драйвер, группы, фактический offload и выбранное устройство; fallback не принимается. |
| `GPU_SELECTION`, `GPU_UNSUPPORTED` | Явный UUID/индекс адаптера, поддерживаемый GFX target; проверьте inventory и матрицу GPU выше. |
| `CONFIG_*`, `PROJECT_CHANGE`, `DEVICE_CHANGE` | Приватный `.env`, прежнее имя проекта, явное переключение устройства. |
| `MODEL_DOWNLOAD`, `SOURCE_DOWNLOAD`, `PYTHON_*`, `TOOLS_DOWNLOAD` | Сеть и кеш; повторить ту же setup-команду после устранения причины. |
| `MODEL_DRIFT`, `MODEL_DIGEST`, `SOURCE_INTEGRITY`, `MODEL_MANIFEST` | Сохранённый pin, целостность weights и source snapshot. |
| `MODEL_EXPORT` | Python 3.12 exporter, disk TMPDIR, свободное место и partial output. |
| `NPU_SOCKET`, `NPU_RUNTIME`, `NPU_PROFILE`, `NPU_PID` | `logs/npu/runtime.log`, доступ к сокету, PID и профиль. |
| `UI`, `API`, `INDEX` | Compose logs frontend/backend/Ollama, готовность БД и индекса. |
| `MODEL_RESPONSE`, `MODEL_SOURCES`, `MODEL_QUALITY`, `MODEL_EMBEDDING` | Ответ реальной модели, синтетические источники и качество; ошибка не маскируется. |

Обычные тесты CLI детерминированы: API, скачивания и модели
заменены заглушками. Восстановление `pip` проверяется на локальном временном
venv без доступа к сети; тестовому Python нужны модули `venv` и `ensurepip`.
Тесты не устанавливают веса и не доказывают аппаратную
совместимость ноутбука. Запуск:

```bash
python3 -m unittest discover -s runtime/setup -v
python3 -m compileall -q runtime/setup project-creator
```
